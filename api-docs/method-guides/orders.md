# Заявки

Методы этого раздела сгруппированы по назначению. Для каждого метода указаны контрактные сведения из Swagger; поля и ограничения, которых нет в спецификации, здесь не предполагаются.

Источники:

- `openapi/swagger-core.yaml`

## Кратко по методам

| Метод | Для чего | Как указать объект и данные | Что меняет / возвращает |
|---|---|---|---|
| `GET`<br>`/api/v1/orders (заказчик)` | Поиск заявки | В query: `page`, `batchSize`, `state`, `category`, `templates`, …. Заголовок: `ZakupayToken`. | Возвращает: `count`, `orders`. |
| `POST`<br>`/api/v1/orders (заказчик)` | Создание заявки | В query: параметры формата ответа/дат. В теле: `name`, `additionalDataJson`, `project`, `state`, `consignee`, `comment`, …. Заголовок: `ZakupayToken`. | Выполняет действие «создание заявки». Данные: Название заявки (`name`); Массив данных в котором обязательно указание значения nameCell1… (`additionalDataJson`); Проект заявки (`project`); Статус заявки (`state`); `consignee`; …. Ответ: `result`, `order`. |
| `PATCH`<br>`/api/v1/orders (заказчик)` | Редактирование заявки | В теле: `id`, `name`, `project`, `state`, `comment`, `externalId`, …. Заголовок: `ZakupayToken`. | Обновляет: ID заявки (`id`); Название заявки (`name`); `project`; Статус заявки (`state`); Комментарий к заявке (`comment`); …. Ответ: `result`, `order`. |
| `GET`<br>`/api/v1/orders (поставщик)` | Поиск заявки | В query: `company`, `category`, `status`, `count`, `creationDateFrom`, …. Заголовок: `ZakupayToken`. | Возвращает: `count`, `orders`. |
| `GET`<br>`/api/v1/orders/{id}/offer-compare-report` | Получение файла сравнения счетов | В URL: `id` — ID заявки. Заголовок: `ZakupayToken`. | Возвращает: `string (поля в Swagger не раскрыты)`. |

Подробные параметры, поля, ответы и ошибки для каждого метода — ниже.

## `GET /api/v1/orders (заказчик)`

**Название в Swagger:** Поиск заявки.

**Описание Swagger:**

Поиск заявок по различным параметрам. Выбираются заявки или по доступным проектам, или если текущий пользователь создатель или ответственный по заявке.


Метод предоставляет возможность запрашивать коллекцию заявок постранично, максимальное количество заявок на странице задается параметром `batchSize` (стандартное значение = **10**, максимальное значение = **100**), для загрузки страниц используется параметр `page`. Также доступны различные способы по фильтрации заявок.

__Метод доступен если пользователь__:

        - авторизован;

        - имеет доступ к системе;

        - состоит в какой-либо компании;

        - имеет право `ORDERS`;

        - авторизован;

        - имеет право `ORDERS_CREATE`;

Для создания пользователем заявок по заданному проекту должно выполняться два условия:

  - пользователь в принципе имеет право на создание заявок

## `DELETE /api/v1/orders/{id}`

**Название в Swagger:** Удаление заявки.

**Описание Swagger:**

Позволяет удалить заявку и связанные с ней счета. Описание необходимых прав и условий: Как определяется возможность удаления ПОЗИЦИИ заявки:
 (Шаги проверки по порядку)
  1) Если у позиции есть mergeChilds (то есть заявку позиции объединили), то позицию удалять НЕЛЬЗЯ
  2) Если у заявки этой позиции нет счетов и текущий пользователь - это создатель заявки, то позицию удалить МОЖНО.
  3) Если у позиции заявки нет счетов  или нет счетов, переданных на согласование (статусы READY_FOR_ACCEPT, ACCEPTED_BY_ACCEPTORS, PAID) и есть право  ORDERS_EDIT_BEFORE_ACCEPTED_OFFER), то проверяется следующее по порядку:

    3.1) Заявка в статусе черновик (DRAFT) и текущий пользователь создатель заявки и есть право ORDERS_CREATE, то удалить МОЖНО.

    3.2) Заявка создана в дереве компаний текущего пользователя и есть право  ORDERS_DELETE, то удалить МОЖНО.

    3.3) Проверяется право ALL_DATA_FROM_ALL_COMPANIES, если оно есть, то удалить МОЖНО, иначе НЕЛЬЗЯ.

  4) Если ничего из этого не выполнилось, то удалить позицию НЕЛЬЗЯ

  Как определяется возможность удаления самой заявки:
  1) Проверяется, что пользователь может удалить все позиции заявки, если какую-то позицию удалить нельзя, то всю заявку удалить так же нельзя.

  Все остальные шаги РОВНО такие же как и при проверке удаления позиции, за исключением (3.2), там вместо проверки принадлежности дереву компании можно обойтись правом ORDERS_ALL, т.е.
  (заявка создана в дереве компаний текущего пользователя ИЛИ имеется право ORDERS_ALL)
