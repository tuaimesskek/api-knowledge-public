# Платежи: понятная инструкция по методам API

В этом разделе разобраны все четыре метода группы «Платежи»: получение списка, создание или редактирование, обновление фактических данных и удаление.

Платёж связан со счётом (`offer`). У счёта и у платежа свои идентификаторы: `offerId` — ID счёта, `offerPaymentId` — ID платежа. Во всех методах нужен заголовок авторизации `ZakupayToken`.

## Коротко: какой метод выбрать

| Что нужно сделать | Метод |
|---|---|
| Найти платежи и получить их данные | `GET /api/v1/payments` |
| Создать платёж либо изменить его плановые параметры или статусы | `POST /api/v1/offer/{offerId}/payment-save` |
| Обновить фактические данные платежа, уже принятого к оплате | `PUT /api/v1/offers/{offerId}/payments/{offerPaymentId}` |
| Удалить платёж | `DELETE /api/v1/offers/{offerId}/payments/{offerPaymentId}` |

`POST` и `PUT` действительно оба умеют менять существующий платёж. Разница — в сценарии и контракте: `POST` — универсальное сохранение (создание или редактирование по ID в теле запроса); `PUT` — обновление фактических реквизитов уже существующего платежа, ID которого указан в URL. Для `PUT` платёж обязательно должен быть принят к оплате.

## 1. Получить список платежей

```http
GET /api/v1/payments
```

Метод возвращает платежи, доступные пользователю. Можно запрашивать их постранично и фильтровать по счёту, заявке, статусу, датам, валюте, создателю или ответственному по заявке.

Часто используемые параметры:

| Параметр | Значение |
|---|---|
| `page` | Номер страницы; по умолчанию `1` |
| `pageSize` | Размер страницы; по умолчанию `10`, максимум `100` |
| `offerId` | ID счёта |
| `orderId` | ID заявки |
| `accepted` | Принят ли платёж к оплате (`true`/`false`) |
| `paymentDateFrom`, `paymentDateTo` | Диапазон фактических дат оплаты (`yyyy-MM-dd`) |
| `planPaymentDateFrom`, `planPaymentDateTo` | Диапазон плановых дат оплаты (`yyyy-MM-dd`) |
| `updatedTimeFrom`, `updatedTimeTo` | Диапазон дат последнего изменения (`yyyy-MM-dd`) |
| `createdDateFrom`, `createdDateTo` | Диапазон дат создания (`yyyy-MM-dd`) |
| `currency` | ID валюты; параметр можно передать несколько раз |
| `hasNonMainCurrency` | Фильтр платежей в валюте, отличной от основной (`true`/`false`) |
| `totalCount` | Запросить общее количество подходящих платежей |

Пример запроса:

```http
GET /api/v1/payments?offerId=78&accepted=true&page=1&pageSize=25
ZakupayToken: <ваш токен>
```

Метод доступен авторизованному пользователю с доступом к системе и правом `OFFERS`. Ответ содержит массив `payments` и сведения о странице. Поля платежа включают, например, `id`, `offer.id`, `amount`, `number`, `accepted`, `paymentDate` и `planPaymentDate`.

## 2. Создать или отредактировать платёж

```http
POST /api/v1/offer/{offerId}/payment-save
```

`offerId` передаётся в URL. Тело запроса может содержать:

| Поле | Назначение |
|---|---|
| `id` | ID существующего платежа. Передавайте его при редактировании; для создания в схеме он не указан как обязательный |
| `amount` | Сумма в валюте счёта |
| `amountInMainCurrency` | Сумма в основной валюте пользователя, если валюта счёта отличается |
| `number` | Номер платёжного документа |
| `planPaymentDate` | Запланированная дата оплаты |
| `paymentDate` | Фактическая дата оплаты |
| `isPaid` | Признак, что платёж оплачен |
| `accepted` | Признак, что платёж принят к оплате |

Пример редактирования по ID (пример иллюстрирует состав полей; используйте реальные ID и допустимый для API формат даты):

```http
POST /api/v1/offer/78/payment-save
ZakupayToken: <ваш токен>
Content-Type: application/json

{
  "id": 114,
  "amount": 30000,
  "planPaymentDate": "2026-10-30T00:00:00.000Z",
  "accepted": true
}
```

По описанию метода, для сохранения требуется право `OFFERS_PLAN_PAY` или `OFFERS_PLAN_PAY_WITHOUT_NOTIFICATIONS` и доступ к счёту. Дополнительные права зависят от операции:

- для изменения номера платёжки или отметки об оплате нужно одно из прав `OFFERS_PAY`, `OFFERS_PAY_BY_PREPAID_OFFERS`, `OFFERS_PAY_WITHOUT_NOTIFICATIONS`;
- для установки `accepted: true` нужно `OFFERS_PAY_APPROVE` или `OFFERS_PAY_APPROVE_WITHOUT_NOTIFICATIONS`.

В спецификации для `amount` написано, что сумма должна быть больше нуля и меньше текущей суммы платежа. Среди описанных ошибок также есть «Превышена сумма по счёту» и «Платеж имеет нулевую сумму». Если для вашего сценария сумма должна увеличиваться, уточните допустимое поведение у владельца API: формулировки опубликованной схемы не дают надёжно определить все правила перерасчёта.

## 3. Обновить фактические данные уже принятого платежа

```http
PUT /api/v1/offers/{offerId}/payments/{offerPaymentId}
```

Оба ID находятся в URL. Метод предназначен для изменения данных существующего платежа и требует, чтобы он уже был **принят к оплате**. Тело запроса по схеме:

| Поле | Обязательность | Назначение |
|---|---|---|
| `date` | Да | Фактическая дата выполнения платежа |
| `number` | Да | Номер платёжного документа (до 256 символов) |
| `amount` | Нет | Сумма в валюте счёта |
| `amountInMainCurrency` | Нет | Сумма в основной валюте пользователя для платежа в другой валюте |

Пример:

```http
PUT /api/v1/offers/78/payments/114
ZakupayToken: <ваш токен>
Content-Type: application/json

{
  "date": "2026-10-05T00:00:00.000Z",
  "number": "PAY-114",
  "amount": 30000
}
```

Нужно право `OFFERS_PAY`. Также должны выполняться условия связи пользователя со счётом: например, запрос счёта отправлен его компанией, счёт выставлен на её банковский счёт либо среди связанных заявок есть заявки этой компании. Если платёж ещё не принят к оплате, метод возвращает ошибку.

**Как выбрать между `POST` и `PUT`:** меняете плановую дату, создаёте платёж, меняете флаг акцепта или оплаты — ориентируйтесь на `POST`; фиксируете номер и фактическую дату уже принятого платежа — на `PUT`. Некоторые поля пересекаются (например, сумма и номер), поэтому при неоднозначном сценарии учитывайте права пользователя и статус платежа.

## 4. Удалить платёж

```http
DELETE /api/v1/offers/{offerId}/payments/{offerPaymentId}
```

ID счёта и платежа передаются в URL. У пользователя должны быть права `OFFERS_PAY` и `OFFERS_PAY_DELETE`, а платёж должен принадлежать указанному счёту. Успешный ответ — строка `Платёж удалён.`

Пример:

```http
DELETE /api/v1/offers/78/payments/114
ZakupayToken: <ваш токен>
```

## Ошибки и проверки перед запросом

Перед изменением проверьте, что:

1. `offerId` — ID нужного счёта, а `offerPaymentId` — ID платежа именно по этому счёту.
2. Пользователь имеет право на нужный сценарий и доступ к этому счёту.
3. Для `PUT` платёж принят к оплате, а в теле присутствуют `date` и `number`.
4. Для `POST` передан `id`, если редактируется существующий платёж, и выставлены только те статусы, на изменение которых есть права.
5. Даты, суммы и валютные поля соответствуют схеме и правилам счёта.

Для методов изменения спецификация описывает ошибки `400` (недопустимые данные или состояние), `404` (счёт/платёж не найден либо платёж не принадлежит счёту) и `403` (нет доступа к счёту). Конкретные тексты ошибок различаются между методами.

## Границы описания

Инструкция пересказывает опубликованный OpenAPI. Она не подтверждает поведение конкретной учётной записи или окружения. В самой схеме есть места, где типы дат и примеры представлены неодинаково; точный формат даты для конкретного метода сверяйте с контрактом и ответами вашего контура. Права перечислены по описаниям методов и не заменяют проверку настроек пользователя.

Источники:

- `openapi/swagger-core.yaml` — схемы запросов, ответы, ограничения и описания методов платежей.
- `api-docs/endpoint-index.md` — индекс методов основного API.
